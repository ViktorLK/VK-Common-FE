# VK.Blocks FE: Development Lifecycle (DL)

### DL.01 — Testing

- **Unit Tests**: Test pure functions, hooks (via `renderHook`), and utility modules in isolation. Mock ALL external dependencies (API calls, browser APIs, third-party SDKs).
- **Component Tests**: Use React Testing Library for component behavior testing. NEVER test implementation details (internal state, lifecycle methods). Test what the user sees and does.
- **Integration Tests**: Use Playwright or Cypress for critical user flows (auth, checkout, data mutations).
- ALL exported hooks and utility functions MUST have unit tests covering:
    - ✅ Happy path (normal input → expected output)
    - ✅ Edge cases (empty input, boundary values)
    - ✅ Error handling (network failure, invalid data)
    - ✅ Loading/pending states
- **Naming**: Test file: `{targetFile}.test.ts(x)`. Test suite: `describe('{ComponentName}')`. Test case: `it('should {behavior} when {condition}')`.
- **Project**: Test files MUST be co-located with source files OR in a `__tests__/` directory within the same feature folder.

### DL.02 — Code Generation

- NEVER generate partial or placeholder code (e.g., `// TODO`, `// implement here`).
- ALL generated code MUST be immediately runnable without errors.
- NEVER omit import statements or type declarations.
- If a complete implementation requires additional context, ASK before generating.
- **TypeScript**: ALL generated code MUST pass `tsc --noEmit` without errors. NO `@ts-ignore` or `@ts-expect-error` without explicit justification.

### DL.03 — Architecture Decision Trigger

**Trigger Conditions** — Proactively prompt when ANY of the following occurs:

- A shared type contract / interface is introduced or modified
- A design pattern is adopted or replaced (e.g., state management strategy, data fetching approach, component composition pattern)
- Cross-cutting concerns are refactored (e.g., auth flow, error handling, i18n strategy, theming)
- A technical trade-off is explicitly resolved
- An existing approach is intentionally abandoned in favor of another

**Required Action**

Interrupt the current flow and ask:

> "⚠️ An architectural decision point has been detected.
> Should I generate an ADR to record this decision before we continue?"

If confirmed → generate an ADR in `docs/02-ArchitectureDecisionRecords/`.
Goal: Ensure _why this change was made_ is captured in real time, not reconstructed retroactively.

### DL.04 — Backlog Synchronization Trigger

**Trigger Conditions** — Proactively prompt when ANY of the following occurs:

- A `README.md` is created or updated with a "Future Roadmap", "Roadmap", or "今後の展望" section.
- A `// TODO`, `// FIXME`, or `// DEBT` comment is **discovered in existing code** during review or audit (DL.02 prohibits introducing new ones).
- A technical improvement is identified but deferred (e.g., "non-urgent refactoring").
- A technical debt item is discussed during the conversation.

**Required Action**

Interrupt the current flow and ask:

> "⚠️ A potential backlog item (Technical Debt/Roadmap) has been detected.
> Should I generate an atomic task in `docs/05-Backlogs/`?"

If confirmed → collect title, description, and module from context and create the backlog item.

### DL.05 — Type Safety & Codegen Documentation

**Mandatory Tagging** — ALL code elements that interact with or are driven by code generation tools MUST be documented:

- **`[CODEGEN]`**: Used for files auto-generated by tools (e.g., API client types from OpenAPI, GraphQL codegen, Prisma client).
    - _Format_: `// [CODEGEN] - This file is auto-generated by {Tool}. DO NOT edit manually.`
- **`[SCHEMA]`**: Used for Zod schemas or type definitions that serve as the single source of truth for validation and type inference.
    - _Format_: `// [SCHEMA] - This schema is the source of truth for {Entity} validation and TypeScript types.`
- **`[DERIVED]`**: Used for TypeScript types derived from schemas or other sources.
    - _Format_: `// [DERIVED] - This type is inferred from {SchemaName}. Do not define manually.`
